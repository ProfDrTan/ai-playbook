2b · How to read the open and close — reliable sources

Use Yahoo Finance's daily History page. It is the source of record for all three instruments.

InstrumentHistory page
S&P 500 (^GSPC)finance.yahoo.com/quote/%5EGSPC/history/
Nasdaq-100 (^NDX)finance.yahoo.com/quote/%5ENDX/history/
Gold futures /GC, Dec 2026 (GCZ26.CMX)finance.yahoo.com/quote/GCZ26.CMX/history/
  1. Open the History page for the instrument.
  2. Set the time period to cover the dates you need, and the frequency to Daily.
  3. Find the row for the date. Read the Open and Close columns. Use Close, not Adj Close, for the prediction and for scoring.
  4. Record the value, the date, the page URL and the time you read it. If Yahoo's Download button is unavailable to you, reading the row on screen is enough.

Which dates to record

DateRecordUsed for
Fri 25 SepClose (all three)Baseline; the gold direction is measured against it
Mon 28 SepOpen and Close (all three)Agent inputs
Tue 29 Sep, before the lockLatest available CloseAgent inputs
Fri 2 OctClose (all three)The target, used for scoring

Rules that keep it fair

  • One number of record. You read the Fri 2 Oct Close from Yahoo and post it by Sat 3 Oct 12:00 SGT (US close is early Sat 3 Oct SGT). That posted figure is the one everyone is scored on, even if Yahoo revises it afterwards.
  • Same source for both dates. Gold direction compares two Closes from the same page. If Yahoo is unavailable, use Google Finance for SPX and NDX, and for gold use one alternative source for both dates. Never mix sources.
  • Futures caveat. COMEX gold trades almost around the clock, so its "Close" is the last price of Yahoo's daily bar and can differ from the official exchange settlement. That is why the source, the exact contract and both dates are fixed in advance.
  • R4 commits actuals/vW4.json (date, open, close, source URL, time read) for the dates above; the Fri 2 Oct value goes in by Sat 3 Oct 18:00 SGT. Stage 6 reads from it.
  • A tie on gold (identical Close on both dates) is void.

3 · Preserving the integrity of the prediction

Cutoff: Tuesday 29 Sep 2026, 23:59:59 SGT (= 15:59:59 UTC)

  1. The clock is GitHub's, not the team's. A team's entry is the last push to main made at or before the cutoff, using GitHub's server-side push time. Commit timestamps are set by whoever commits, so they are not used.
  2. The lock job archives it, outside the teams' reach. It copies the file into dt3-monitor under locks/vW4/<team>.json together with the commit SHA, push time and a SHA-256 hash of the content. Every student has read-only access to dt3-monitor (I checked all 31 collaborators; only you have write), so no team can alter the archive.
  3. Scoring uses the archived copy only. Whatever happens to the team's file afterwards — edited, renamed, force-pushed — is irrelevant. A team that changes its file later simply has a file that no longer matches its locked hash.
  4. Hashes are announced. Right after the lock, the hash per team goes to Discord and onto a public ledger. A hash reveals nothing about the prediction, but anyone can verify their own.
  5. No entry means no entry. No file, an invalid file, or a push after the cutoff: 0 points and "NO ENTRY" on the leaderboard. There is no "I thought I submitted" — see the pre-lock status board below.

Pre-lock status board (participation lever)

At Tue 12:00, 20:00 and 23:00 SGT the monitor posts VALID / INVALID / MISSING for each team to Discord — status only, never the values. This is the pressure that gets R1s chasing their teams before midnight, and it removes any excuse.

Two facts that shaped the design

  • The monitor's schedule cannot be the cutoff. dt3-monitor is set to run every 10 minutes, but its recent runs land 3–5 hours apart, and every one of the last 8 has ended in failure at the "Publish history to public site" step (the Discord half succeeds). So the cutoff is a time in the data, evaluated whenever the lock job runs, and the lock job is run manually on Wed morning rather than left to a 23:59 cron.
  • Whether teams can read each other's repos is unverified. All four team repos are private, but my token cannot see the org's base permission. If it is anything above "none", a team could read a rival's file before the cutoff. Check it before release. Fallback if needed: submit only the SHA-256 hash by Tuesday, and reveal the file after Friday's close.

Ways this could be gamed, and the answer

AttemptDefence
Push after midnight, backdate the commitCutoff uses server-side push time, not commit dates
Edit the file after seeing Wednesday–Friday movesScoring reads the archived copy; a changed file mismatches its locked hash
Force-push or rewrite history after the lockArchive is a copy in a repo teams cannot write to; a locked SHA that is no longer reachable is flagged
Submit on a branch or in a forkOnly main of the team repo counts
Delete or rename the file, re-create it later (Sprint 3 Team 1 pattern)Lock records what was present at the cutoff; a later re-creation cannot change it

6 · UI consistency across teams

Sprint 3's four dashboards differ a lot: Team 1 has Human Score, comparison table, chart and OHLC table; Team 2 has charts, tables and a macro comparison; Team 3 has the largest and most styled build; Team 4 has one bar chart and a text summary. The code also lives in four different places, and Teams 1–2 read CSV while Teams 3–4 read JSON. The fix is to fix the structure, the data and the location, and leave the styling free.

  1. Fixed location. Every dashboard lives at ui/index.html in the team repo, so all four are found and opened the same way.
  2. Five required panels, same names, same order, one per stage. Each carries a fixed attribute so it can be checked automatically:
    PanelAttributeData file it reads
    Locked Prediction (with lock time)data-panel="locked-prediction"data/locked_prediction.json
    LLM Synthesisdata-panel="llm-synthesis"data/llm_synthesis.json
    Human Scoredata-panel="human-score"data/human_score.json
    Deltadata-panel="delta"data/delta.json
    Prescriptiondata-panel="prescription"data/prescription.json
  3. Fixed data contract. The UI reads only these JSON files, never typed-in numbers. Proposed required fields:
    FileRequired fields
    locked_prediction.jsonsprint, team, locked_at, spx_close, ndx_close, gold_direction, sha256
    llm_synthesis.jsonper instrument: each model's view, agree (yes/no), divergence note
    human_score.jsonper instrument: score, decision (confirm / adjust / override), justification
    delta.jsoninstrument, predicted, actual, error, error_pct, direction_correct, top contributing agent
    prescription.jsonagent, weight change, reason
    Because every team uses the same schema, any team's dashboard could display any team's data. The lock job writes a display copy of locked_prediction.json into each team repo; scoring never reads it (it uses the archive in §3), so editing it gains nothing.
  4. Starter template. A skeleton in team-template: the five panels stubbed, sample JSON files, and a loader. Teams restyle and extend it. This is the strongest measure because it prevents the divergence rather than correcting it. NOT BUILT Needed by Tue 29 Sep 12:00.
  5. Automated check. dt3-monitor checks each team repo for ui/index.html, all five panel attributes and all five data files parsing correctly, and posts pass/fail per team to Discord. NOT BUILT
  6. Free: colours, layout, charts, extra panels. Extras are welcome (Team 3's and Team 1's extras stay), but the five required panels must be present.
