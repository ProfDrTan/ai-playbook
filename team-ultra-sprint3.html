The actual goal

"Introduce the first automated data pull (SPX weekly close), while keeping the narrative/judgment layer fully human-written — automation replaces data-gathering, not thinking." — sprint3-draft.html, current working draft

That's narrower than it sounds. One data point, automated. Everything else — the read on it — stays a person's call. Below is what building exactly that, for real, actually involves.

Where it broke

1 · No free, key-less data source actually reaches a locked-down build environment

"Automate the pull" assumes a script can just fetch a number. In practice every no-signup market-data endpoint (Yahoo's undocumented endpoints, most free tiers) either requires an API key or isn't reachable from a sandboxed environment with an allowlisted network — this build hit exactly that wall. The only way through, without a paid key, was a manual verified read of two cited sources. That's not automation; it's a human doing the "automated" step by hand and calling it done. A team without a data-provider API key (Alpha Vantage, Polygon, etc.) will hit this same wall and either fake the automation, burn time getting a key approved, or quietly fall back to manual entry without saying so.

2 · The two "authoritative" sources don't agree on freshness

FRED's SP500 series — the St. Louis Fed's own feed — was still showing 2026-09-17 as its latest observation when checked on Sep 22, a multi-day lag behind same-day market reporting. If "verify against a second source" is the instruction, a team needs to be told in advance which source is authoritative when two disagree, or every team invents its own tie-breaker rule silently.

3 · No published schema for where the pull's output lives

This is the exact blocker sprint3-draft.html already flags from Sprint 1/2 — "there's no template" — and it reappears here. Nothing in the current draft says whether the automated SPX value should land as a JSON file, a CSV row, a commit message, or a FigJam card. Four teams will make four different choices, and R4 (Data & Calibration) has nothing consistent to calibrate against.

4 · Two sources of truth disagree on scope

The CP3405 planning notes describe Sprint 3 as a six-role deliverable — R1 through R6 each producing a distinct artifact (macro update, technical indicator, calibration check, human score, LLM/GitHub component, FigJam board). sprint3-draft.html — the actual working draft — scopes Sprint 3 far narrower: one automated data pull, everything else continuing as manual Sprint-2-style work. A team (or an AI) building from the planning notes alone would over-build; building from the draft alone would under-deliver on the six-role framework. Worth resolving which document is current before either goes out.

What worked

The narrow scope is buildable. A verified SPX close, cited to two sources with the disagreement between them documented rather than hidden, plus a one-paragraph human-written read on why it moved (chip-stock rally, not a macro surprise) — that's a clean, honest version of "automation replaces data-gathering, not thinking." The failure mode isn't the concept; it's that nothing in the current spec tells a team what to do when the data source itself doesn't cooperate.

Recommendation

  1. Name one authoritative SPX source in the Sprint 3 page itself, with a stated fallback if it's unreachable — don't leave teams to invent one.
  2. Ship the output schema (file name, format, location) with the sprint instructions, not as a mid-week patch — the same fix already identified for Sprint 1/2's template gap.
  3. Reconcile the CP3405 planning notes against sprint3-draft.html before either is finalized — right now they'd produce two different assignments.
