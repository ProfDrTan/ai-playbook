Fix Before Next Trimester: What Sprint 9 of TR3 2026 Taught Us

Everything below went wrong, or nearly went wrong, during Sprint 9A of TR3 2026 (2–8 November). Each lesson ends with the fix to build in before Week 1 of the next trimester, so the same problem cannot come back.

Draft for review · Written 7 Nov 2026

1. Deadlines and evidence

A deadline check must not depend on a chat session

What happened
The milestone 1 check (Tue 3 Nov 23:59) was started at 23:09 and stopped at 23:40, before the deadline. When it resumed at 07:03 the next morning, Team 1’s backlog cards had appeared at some unknown time in between. The result had to be given as “on time” on the benefit of the doubt.
Why
FigJam keeps no server timestamp that can be read for when a card was added. Only GitHub records arrival time on its own servers.
Fix before Week 1
Every FigJam backlog is also committed to GitHub as docs/backlog-N.md by the same deadline, so its arrival time is recorded by GitHub. Deadline checks run as a scheduled job in the monitor repo at each deadline, not in a chat.

The automation account needs permission to automate

What happened
A job to fetch the official Friday closes from Yahoo could not be added to the monitor repo: the access token was refused for workflow files. Yahoo is also blocked from Claude’s own sandbox.
Why
The token had permission to change files, but not the workflows permission GitHub requires for anything under .github/workflows/.
Fix before Week 1
Issue the course token with the workflows permission (expiry 366 days or less, as the organisation requires), and test it by adding one harmless workflow before the trimester starts.

One official source for the actual closes

What happened
Students measure their errors against Yahoo closes. The instructor-side check had to use IBKR instead. Index closes match, but gold was COMEX’s last trade rather than Yahoo’s close, so gold errors could differ slightly.
Fix before Week 1
A scheduled job in the monitor repo fetches the Friday closes from Yahoo every Saturday morning SGT into one file. Students and the scoreboard both read that file, so there is exactly one set of “actual” numbers.

The monitor reported “failure” on every run

What happened
Every monitor run showed as failed, even though the Discord and GitHub data were saved correctly. Only the last step, publishing history to the public site, was failing.
Fix before Week 1
Fix or remove the failing publish step, so a red run means something is genuinely broken.

2. Files, formats and paths

The prediction format changed almost every week

What happened
When Sprint 9A asked teams to look back at their predictions from vW4 to vW8, the files were not comparable. Field names changed week to week (team_call, predictions, macro_predictions). Some yields were stored as text such as “5.12%”. Gold was a direction (“DOWN”), not a number, for the first two weeks. Some weeks had no numbers at all.
Why
The format grew sprint by sprint as new instruments were added. A single common format was only introduced in Sprint 9A, for vW9.
Fix before Week 1
Publish one prediction format before the first prediction sprint and never change it: week, target_date, then SPX, NDX, GOLD, TNX as plain numbers. Every instrument is a number from the first week. If an instrument is added later, it is added as a new field, and the existing fields stay as they are.

Typos become data

What happened
Two locked predictions had the 10-year yield at 4.08 and 4.15 when it was trading around 5.1. Any rule built on past errors, such as removing a team’s bias, is distorted by entries like these.
Fix before Week 1
A check runs on every push to a team repo and flags any prediction more than 10% away from the latest close as a likely typo, before the lock rather than after it.

Right content, wrong place

What happened
One team saved its old-predictions table at data/old_predictions/predictions.csv instead of data/old_predictions.csv and missed the milestone. Another committed a blank peer-check template under a different file name.
Fix before Week 1
Every team repo starts from the template repo with every required file already present as an empty stub, at its exact path. The check on every push reports any required file that is missing or misplaced. Every brief ends with a path checklist.

Sealed files were edited

What happened
While building the old-predictions table, one team’s commit also changed two of its sealed prediction files from earlier weeks (a renamed field, a removed data block). The predicted numbers did not change, but the record was no longer original.
Fix before Week 1
Once a week’s lock passes, its prediction file is read-only. The check on every push flags any change to a past prediction file, and the scoreboard shows it.

Records written before the event they record

What happened
Two teams’ Sprint 8 live-test records (docs/live-test.md) reached GitHub before the live test took place, so neither counted. No team had a valid peer check.
Fix before Week 1
Every record of an in-class event has a template with the event’s date and time at the top, and only counts if it reaches GitHub after the event starts. The brief says so in one line.

3. Prediction design

Nobody compared against doing nothing

What happened
A replay of the teams’ own predictions showed all four teams predicting too high for weeks, during a falling market. Their locked numbers were no more accurate than simply repeating Tuesday’s close: one team tied that baseline and three did worse.
Why
Errors were only measured in Week 9, so the bias went unnoticed for five weeks, and there was no baseline to compare against.
Fix before Week 1
From the first prediction sprint, each week’s error is measured automatically on Saturday, next to the do-nothing baseline (the last close known at the lock). Teams see their bias from week two, not week nine.

Before-and-after cannot tell you whether a change worked

What happened
Sprint 9B had to be designed late to test each team’s change properly. A smaller error next week could just mean an easier week.
Fix before Week 1
Make the A/B lock the standard way to test any change: the old method and the new method are both locked for the same week, and both are scored against the same close. Plan the last sprints around it from Week 1, so the trimester ends with the loop the architecture describes: prediction, error, change, tested result.

4. Running the class

Public visibility changed behaviour within a day

What happened
After the Scrum Scoreboard was announced on 4 November, every team was pushing work in the hours before the next deadline. The weakest team’s Discord activity went from 1 message in 48 hours to 28, and two teams that had no backlog added one.
Fix before Week 1
Launch the scoreboard from Sprint 3, not Sprint 9. Publish its rules on day one, including two decided in advance: an unprovable arrival time is given the benefit of the doubt, and whether one missed item may fail two checks.

Every presenting sprint needs its template with the brief

What happened
Sprint 9A had no presentation because of the 9 November public holiday, and the Sprint 9B template was only built afterwards.
Fix before Week 1
For every sprint that ends in a presentation, the template is released together with the brief, and every number on it comes from a file the team already has to commit.
